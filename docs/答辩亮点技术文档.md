## 一、项目总览

校园二手物品共享平台是一个前后端分离的 C2C 交易系统，面向校园场景提供闲置物品的发布、浏览、交易与治理全流程能力。

### 技术栈

| 层 | 技术选型 | 版本 |
|----|---------|------|
| 后端框架 | Spring Boot | 3.3.5（JDK 17） |
| ORM | MyBatis-Plus | 3.5.9 |
| 数据库 | MySQL | 8.0 |
| 缓存与分布式锁 | Spring Data Redis + Lettuce 连接池 | — |
| 认证 | JJWT（HMAC-SHA384 签名） | 0.12.6 |
| 密码加密 | Spring Security Crypto（BCrypt） | — |
| 工具库 | Hutool | 5.8.25 |
| 前端框架 | Vue 3 + Vite | — |
| UI 组件 | Element Plus + Icons | — |
| 状态管理 | Pinia | — |
| 路由 | Vue Router 4 | — |
| HTTP | Axios | — |
| 可视化 | ECharts | — |

### 架构分层与数据流

```
Vue SPA（views / components / stores）
   ↓ axios（request.js 统一封装，自动携带 Bearer Token）
Vite 代理 /api
   ↓
Spring Boot：JwtInterceptor（认证 + 小黑屋拦截）
   ↓
Controller → Service → Mapper → MySQL
                   ↕ Redis（分布式锁 / 业务缓存 / 原子计数器）
```

关键工程约定：

- 统一返回格式 `{code, message, data}`，前端响应拦截器统一处理，401 自动清登录态并跳转登录页
- 业务异常统一抛 `BusinessException`，由 `GlobalExceptionHandler` 转换为标准返回，Controller 无 try-catch 噪音
- MyBatis-Plus 逻辑删除 + `MetaObjectHandler` 自动填充创建/更新时间
- `UserContext` 以请求属性透传当前用户身份，Service 层无需层层传递 userId
- Redis 统一降级策略：缓存故障回落 DB，业务不依赖 Redis；Key 按 `lock:/cache:/stat:` 三段分类

## 二、上篇 · 核心亮点

### 2.1 订单状态机与超时预留回收

**背景问题。** C2C 交易有两个典型痛点：一是"拍下不买"——买家下单后长期不付款，商品被无限期锁死；二是并发下单——两个买家同时对同一商品下单，若处理不当会出现一物多卖。

**设计方案。** 用显式状态机约束订单生命周期，用"限时预留 + 定时回收"解决占而不买：

```
PENDING（待付款）→ PAID（已付款）→ SHIPPED（已发货）→ COMPLETED（已完成）
       ↘ CANCELLED（已取消）
```

下单即预留商品 30 分钟，超时自动取消订单并恢复商品在售。

**关键实现。** 核心逻辑在 `OrderServiceImpl`：

1. **状态机**：`STATUS_FLOW` 静态 Map 定义合法流转（PENDING→[PAID, CANCELLED]、PAID→[SHIPPED]、SHIPPED→[COMPLETED]），`updateStatus` 校验目标状态是否在允许列表，非法流转直接抛 `BusinessException`——状态规则集中声明，不散落在各接口。
2. **下单预留**（`createOrder`，Redis 分布式锁 + TransactionTemplate 事务内完成）：
   - 获取 Redis 分布式锁（`campus:sh:lock:order:create:{productId}`），防止并发下单；
   - 校验商品在售、买家不能购买自己的商品；
   - 检查该商品是否已存在他人的未过期 PENDING 订单（`expire_time > now`），有则拒绝——防止一物多卖；
   - 同一买家对同一商品的旧待付订单自动置为 CANCELLED，避免自己占用自己；
   - 订单号用 Hutool 雪花算法生成（`"ORD" + IdUtil.getSnowflakeNextIdStr()`），全局唯一无冲突；
   - 下单成功后商品通过 CAS 条件更新（`WHERE status = 'ON_SALE'`）转 OFF_SHELF（纵深防御），订单设置 30 分钟 `expire_time`；
   - 使用 `TransactionTemplate` 编程式事务替代 `@Transactional`，确保锁覆盖事务提交边界。
3. **超时回收**：`cancelExpiredOrders` 挂 `@Scheduled(fixedRate = 300000)`，每 5 分钟扫描过期的 PENDING 订单，批量取消并调用 `restoreProduct` 将商品从 OFF_SHELF 恢复为 ON_SALE；`payOrder` 时也会实时校验是否超时，双保险。
4. **操作鉴权**：`checkOrderPermission` 按角色细分——付款/确认收货仅买家、发货仅卖家、取消买卖双方皆可，管理员全部放行。
5. 关键写操作使用 Redis 分布式锁 + `TransactionTemplate` 编程式事务，确保锁释放在事务提交之后；商品下架采用 CAS 条件更新作为纵深防御。

**答辩价值。** 这一节体现的是对**并发控制**（Redis 分布式锁防并发下单 + CAS 纵深防御）、**状态一致性**（显式状态机 + 非法流转拒绝）和**事务边界**（TransactionTemplate 确保锁覆盖事务提交）的系统性思考，是评委最常深挖的工程能力点。

### 2.2 小黑屋自动风控算法

**背景问题。** 二手交易天然缺乏信任基础：卖家可能以次充好收割买家，也可能存在职业差评者恶意刷分敲诈卖家。平台需要一套自动识别违规用户的机制，且处罚要有梯度、可救济。

**设计方案。** 定时扫描 + 双规则判定 + 递增刑期的"小黑屋"机制：

- 每日凌晨 3 点自动扫描（`@Scheduled(cron = "0 0 3 * * ?")`），管理员也可在后台手动触发（`triggerScan`）；
- **卖家规则**：收到的评论中 1 星 ≥5 条且占比 >30% → 判定劣质卖家；
- **买家规则**：发出的评论中 1 星占比 >80% 且没有任何成交订单 → 判定职业差评/恶意用户；
- 处罚时长随违规次数指数递增：`14 天 × 2^拉黑次数`（首犯 14 天、再犯 28 天、三犯 56 天……）。

**关键实现。** 核心逻辑在 `BlacklistServiceImpl.autoScan`，数据落在 `t_user` 的四个扩展字段（`blacklist_status/reason/until/count`）：

1. **先解封后扫描**：先把 `blacklist_until` 到期的用户解封，并记入 `justUnblacklisted` 集合从本轮扫描名单中排除——防止"刚解封就因历史数据被再次拉黑"的死循环。
2. **90 天统计窗口**：只统计近 90 天内的 1 星评论，既控制扫描数据量，也避免用户为很久以前的历史违规被反复处罚。
3. **累犯隔离**：曾被处罚的用户（`blacklist_count > 0`）只统计上次解封（`update_time`）之后产生的新评论，保证"一次违规只罚一次"。
4. **卖家评论聚合**：1 星评论按商品归属反查卖家，聚合到卖家维度再判定，而非简单数评论数。
5. **处罚联动通知**：拉黑与解封都通过 `NotificationService.send` 发站内信，写明原因与解封时间，处罚透明可查。

**为什么这么设计（答辩预设追问）：**

- 卖家规则加"≥5 条"门槛：防止小样本误伤——只收到 1 条评论且是 1 星就拉黑显然不公平；
- 30% 占比阈值：容忍正常交易中的个别差评，只惩罚差评成为主流的情况；
- 买家规则加"成交订单数 = 0"条件：真实买家给差评是正当权利，只评论不交易还全给 1 星才是恶意行为特征；
- 翻倍刑期：体现累犯加重的处罚梯度，比固定时长更有威慑力。

**答辩价值。** 这是全项目算法复杂度最高的模块，体现**规则引擎思维**和**边界条件处理**能力（解封-再罚循环、累犯重复处罚、小样本误伤），建议作为主讲亮点之一。

### 2.3 投诉-申诉治理闭环

**背景问题。** 自动风控规则再精细也可能误伤：差评可能源于物流等第三方因素，被拉黑用户需要救济通道；反过来，自动规则覆盖不到的违规行为（欺诈、虚假描述）也需要用户举报入口。治理体系必须闭环。

**设计方案。** 在自动风控之外补两条人工通道，形成完整闭环：

```
自动检测（2.2）→ 处罚 → 用户申诉 → 管理员复核 → 解封
        ↑ 补充
用户投诉 → 管理员处理 → 成立则拉黑被投诉人
```

**关键实现。**

1. **投诉链路**（`t_complaint` 表 + `AdminServiceImpl.handleComplaint`）：投诉记录被投诉人、投诉人、原因、证据图片 URL；管理员处理时状态从 PENDING 流转为 RESOLVED（成立）或 DISMISSED（驳回），并留痕处理人 ID 与备注。投诉成立即调用 `manualBlacklist` 对被投诉人执行 14 天拉黑，同时向投诉人发送“投诉已处理”通知——举报有回音。管理员角色豁免被拉黑。
2. **申诉链路**（`t_appeal` 表 + `handleAppeal`）：被拉黑用户提交申诉理由，管理员审核后流转为 APPROVED 或 REJECTED；通过则立即 `unblacklist` 解封并通知“账号已恢复”，驳回也发通知说明结果——处罚可救济。两条链路均为事务操作。
3. **待办驱动**：`getNotifications` 接口聚合待处理投诉数、待处理申诉数与当前黑名单总数，驱动后台页面的红点提醒，管理员不会漏处理。

**答辩价值。** 这一节展示的是**系统设计完整性**：治理不是“罚了就完”，而是“检测 → 处罚 → 申诉 → 救济”的闭环，且全链路通知留痕、操作可追溯。这是区分“功能堆砌”和“体系设计”的关键论据。

### 2.4 JWT 认证与小黑屋联动拦截

**背景问题。** 认证（你是谁）与风控（你能不能操作）是两个横切关注点。如果在每个 Controller 里各自校验 token、各自查黑名单，代码会大量重复且容易漏配。

**设计方案。** 把两件事都收进 `JwtInterceptor` 拦截器统一处理，并设计“封写不封读”的柔性处罚粒度。

**关键实现。**

1. **认证**（`JwtInterceptor.preHandle`）：OPTIONS 预检请求直接放行；解析 `Authorization: Bearer` 头，`jwtUtil.validateToken` 校验失败返回 401 标准 JSON；校验通过则从 Token 解析出 userId 与 role，注入请求属性，供 `UserContext` 在后续 Service 层取用。
2. **小黑屋联动**：认证成功后调用 `blacklistService.isBlacklisted(userId)`；命中黑名单时，对受限路径 `/product/`、`/comment/`、`/order/`、`/favorite/` 下的**非 GET 请求**返回 403，响应中附带解封时间（“你的账号已被限制使用，解封时间：xxxx”）；GET 请求放行。
3. **前端配合**：`request.js` 响应拦截器收到 401 时清除本地登录态并跳转登录页，Token 过期对用户表现为“自动回到登录页”。

**设计取舍（答辩预设追问）：**

- 为什么“封写不封读”而不是全站封禁？被限制用户仍能浏览商品、查看自己的订单与通知（解封通知需要能收到），只禁止发布、评论、下单、收藏等写操作——处罚有边界，体验不失控；
- 为什么放在拦截器而不是 Service？拦截器一处配置覆盖全部路由，新增接口自动受保护，不会遗漏。

**答辩价值。** 体现**横切关注点集中处理**的架构意识和**权限粒度设计**能力，是讲“拦截器/AOP 思想”的最佳实例。

### 2.5 ECharts 后台数据可视化

**背景问题。** 管理员需要一眼掌握平台运营状况：多少用户、多少商品、订单分布如何、哪些分类最活跃——纯表格无法满足。

**设计方案。** 后台 Dashboard = 四个指标卡 + 两张图表：分类分布玫瑰图、订单状态柱状图；后端聚合统计，前端 ECharts 渲染。

**关键实现。**

1. **后端聚合**：`AdminServiceImpl.dashboard` 返回 `DashboardVO`（用户总数、商品总数、订单总数、今日订单数——今日订单用 `create_time` between 当日零点与 23:59:59 统计）；`/admin/category-stats` 返回各分类商品数量。
2. **前端加载策略**（`Admin.vue`）：`Promise.all` 并发拉取仪表盘、订单、商品三份数据，随后 `nextTick` + 100ms 延时等待 Tab 内 DOM 挂载完成再渲染图表——解决“图表容器尺寸为 0 导致渲染失败”的经典问题。
3. **分类玫瑰图**：`roseType: 'area'` 按面积编码差异，环形样式（内外半径 45%-75%），色板采用主题翠绿的同色系渐变（`#10B981` 起），与全站设计规范一致。
4. **订单状态柱状图**：状态到颜色的语义化映射——待付款 `#F59E0B`（暖橙，提示待办）、已付款 `#3B82F6`、已发货 `#8B5CF6`、已完成 `#10B981`（翠绿，成功态）、已取消 `#9CA3AF`（灰），颜色本身即传达状态含义。
5. **图表生命周期管理**：重新渲染前 `dispose()` 旧实例防内存泄漏；容器所在 Tab 不可见（`offsetParent === null`）时延迟 200ms 重试；监听窗口 resize 调用 `chart.resize()` 自适应；无数据时显示“暂无数据”兜底标题而非空白图表。

**答辩价值。** 体现**前后端数据流的完整链路**和真实的**可视化工程经验**——图表在 Tab 切换、懒渲染、窗口缩放场景下的坑与解法，是评委追问“你真的自己写的吗”时最有说服力的细节。

### 2.6 Redis 分布式锁与多级缓存体系

**背景问题。** 单体架构下多个关键场景存在并发安全与性能瓶颈：一是并发下单可能一物多卖；二是并发收藏可能重复插入；三是定时风控扫描可能被手动触发重复执行；四是商品详情浏览量并发累加出现写覆盖；五是仪表盘聚合查询每次访问都重算四张表。

**设计方案。** 引入 Redis 作为基础设施层，按职责划分为三类能力：

- **分布式锁**（`RedisLockUtil`）：SETNX 获取 + 唯一 token 防误删 + Lua 原子释放 + 自旋等待；
- **业务缓存**（`RedisCacheUtil`）：Cache Aside 模式 + 统一降级（Redis 故障回落 DB，业务不依赖 Redis）；
- **原子计数器**：Redis INCR 原子累加浏览量，替代 read-modify-write 模式。

**关键实现。**

1. **分布式锁工具类**（`RedisLockUtil`）：`tryLock` 用 `setIfAbsent(key, token, ttl)` 原子获取锁；`unlock` 用 Lua 脚本“比对 token + 删除”原子执行，防止误删他人锁；`executeWithLock` 封装自旋等待 + finally 释放的完整生命周期，超时抛 `BusinessException`。
2. **锁与事务边界控制**：`OrderServiceImpl.createOrder` 移除 `@Transactional`，改用 `TransactionTemplate` 编程式事务——锁在 `finally` 中释放，而事务在 `TransactionTemplate.execute()` 内同步提交，确保锁释放在事务提交之后，避免锁释放早于事务提交导致数据不一致。
3. **CAS 纵深防御**：订单创建中商品下架采用 `WHERE status = 'ON_SALE'` 条件更新（`LambdaUpdateWrapper`），即使分布式锁失效也不会超卖。
4. **商品详情缓存**（`ProductServiceImpl.detail`）：Cache Aside 模式，缓存命中则直接返回；缓存前剥离 `favorited` 字段（用户维度字段，防跨用户泄漏），命中后通过 `FavoriteMapper` 单独重算；状态变更时覆写 `updateById`/`removeById` 统一失效缓存。
5. **浏览量原子计数**：用 Lua 脚本 `INIT_INCR_SCRIPT` 原子初始化 + INCR（GET→SET→INCR 三步原子执行），替代原有的 read-modify-write；`syncViewCountToDb` 每 5 分钟 SCAN `stat:product:view:*` 批量回写 MySQL。
6. **分类树缓存**（`CategoryServiceImpl`）：覆写 `save`/`updateById`/`removeById`，任何写操作自动 `delete` 缓存，读操作走 Cache Aside。
7. **仪表盘缓存**（`AdminServiceImpl`）：60 秒 TTL，管理员频繁刷新时不重复查询四张表。
8. **Key 规范**（`RedisKeyConstants`）：统一前缀 `campus:sh:`，按 `lock:/cache:/stat:` 三段分类；TTL 策略：商品 30min、分类 1h、仪表盘 60s。
9. **统一降级**（`RedisCacheUtil`）：读失败返回 null（回落 DB），写失败静默忽略，Redis 故障时业务不受影响。

**答辩价值。** 体现对**分布式基础组件**的系统性运用——分布式锁（SETNX + Lua + 自旋）、锁与事务边界控制（TransactionTemplate）、Cache Aside + 用户维度字段剥离、原子计数器替代写覆盖、统一降级策略。这些是后端工程师的核心工程能力，也是简历和答辩中最常被深挖的技术点。

## 三、下篇 · 全模块速览

### 3.1 用户模块

背景：平台需要身份体系支撑交易与权限区分。实现（`UserServiceImpl`）：密码采用 BCrypt 加密（`BCryptPasswordEncoder`），登录时 BCrypt 匹配验证；禁用账号拦截、用户名/密码错误统一提示防账号枚举；注册先查重再落库；登录成功由 `JwtUtil.generateToken(userId, username, role)` 签发 JWT；`getCurrentUser` 返回前 `setPassword(null)` 脱敏。历史密码迁移：`PasswordMigration` 启动时自动扫描 MD5 格式密码并包裹为 BCrypt(MD5(plain))，登录时 `verifyAndUpgradePassword` 自动升级为 BCrypt(plain)，实现零停机无缝迁移。

### 3.2 商品模块

背景：二手交易的核心是商品的发布、展示与检索。实现（`ProductServiceImpl`）：发布时图片列表以 JSON 数组存储（`JsonListTypeHandler` 自动转换）；编辑/下架校验发布者归属，删除支持管理员越权操作；公开列表默认只展示 ON_SALE 商品；**详情页接入 Redis 缓存**（Cache Aside 模式，30min TTL，状态变更时主动失效），浏览量通过 Redis INCR 原子累加并定时回写 MySQL，替代原有的 read-modify-write 避免并发写覆盖；分页 + 关键词搜索 + 分类筛选的复杂查询写在 Mapper XML 连表实现。

### 3.3 订单模块

状态机、限时预留、定时回收与买卖家分级鉴权——核心亮点，**详见 2.1**，此处不重复。

### 3.4 收藏模块

背景：用户需要标记感兴趣的商品稍后查看。实现（`FavoriteServiceImpl`）：`toggle` 单接口完成收藏/取消切换（存在则删、不存在则增），前端无需维护状态；**并发场景通过 Redis 分布式锁**（`campus:sh:lock:favorite:{userId}:{productId}`）防止快速双击导致重复插入；`t_favorite` 表设 `uk_user_product` 唯一约束在数据库层兆底防重复收藏；收藏列表连表分页返回商品卡片信息。

### 3.5 评论模块

背景：交易完成后需要评价沉淀信用。实现（`CommentServiceImpl`）：对商品发表 1-5 星评分 + 文字内容，按商品分页查询。关键点：评论不只是展示功能，更是**风控算法的数据源**——小黑屋的卖家/买家双规则都基于 1 星评论统计，**详见 2.2**。

### 3.6 通知模块

背景：处罚、申诉等治理动作需要触达用户，不能只靠用户主动查看。实现（`NotificationServiceImpl`）：站内信支持发送、未读数统计、单条/全部标记已读、清理已读；被拉黑、解封、投诉处理、申诉结果等业务事件自动触发通知；`@Scheduled(cron = "0 0 4 * * ?")` 每日凌晨 4 点清理 30 天前的历史通知控制表体积；表上 `idx_user_read (user_id, is_read)` 索引支撑未读数高频查询。

### 3.7 分类模块

背景：商品需要结构化组织以便筛选。实现：`t_category` 以 `parent_id` 自关联实现二级分类树（7 个一级分类 + 30 余个二级），节点携带 Element Plus 图标名与排序字段；`AdminServiceImpl.deleteCategory` 实现删除保护——分类下存在商品时禁止删除，避免产生无分类的孤儿商品。

### 3.8 后台管理模块

管理员工作台：数据概览仪表盘（**详见 2.5**）、用户管理（关键词搜索 + 启用/禁用）、商品管理（查看/删除）、订单管理（按状态筛选）；治理侧支持投诉/申诉处理（**详见 2.3**）、小黑屋名单查看、手动拉黑/解封、手动触发风控扫描。

### 3.9 文件上传模块

背景：商品多图与头像需要图片托管。实现：`FileController.upload` 接收文件交给 `FileUploadUtil` 落盘到 `uploads/` 目录；`FileServerController` 提供 `/uploads/{filename:.+}` 静态访问，`@PostConstruct` 启动时解析绝对路径并自动建目录。**安全亮点：通过 `canonicalPath` 前缀校验阻止路径穿越攻击**（如 `../../etc/passwd`），命中则返回 400 并记录告警日志，并按文件实际类型设置 Content-Type。

评委追问时按此表快速定位；“设计取舍”列如实记录短板与改进方向。

| 技术点 | 代码位置 | 一句话原理 / 设计取舍 |
|--------|---------|-------------------|
| Redis 分布式锁实现 | `RedisLockUtil` | SETNX + 唯一 token + Lua 原子释放 + 自旋等待，防止误删他人锁 |
| 锁与事务边界控制 | `OrderServiceImpl` | `TransactionTemplate` 替代 `@Transactional`，确保锁释放在事务提交之后 |
| CAS 纵深防御 | `OrderServiceImpl.createOrder` | `WHERE status = 'ON_SALE'` 条件更新，即使锁失效也不会超卖 |
| Redis 缓存降级策略 | `RedisCacheUtil` | 读失败返回 null 回落 DB，写失败静默忽略，Redis 故障时业务不受影响 |
| 缓存用户维度字段剥离 | `ProductServiceImpl.detail` | `favorited` 是用户维度字段，缓存前剥离，命中后单独重算，防跨用户泄漏 |
| 浏览量原子计数 | `ProductServiceImpl` + `syncViewCountToDb` | Redis INCR + Lua 脚本原子初始化，替代 read-modify-write；每 5min 回写 MySQL |
| BCrypt 密码迁移 | `PasswordMigration` + `UserServiceImpl` | 启动时 MD5→BCrypt(MD5) 批量迁移，登录时自动升级为 BCrypt(plain)，零停机 |
| 定时任务多实例部署问题 | 订单回收 / 小黑屋扫描 / 通知清理三处 `@Scheduled` | 当前单实例部署无重复执行问题；小黑屋扫描已加 Redis 分布式锁防重复触发 |
| JWT 无状态的注销问题 | `JwtUtil` / `JwtInterceptor` | Token 到期前无法主动失效；取舍：可加服务端黑名单或短有效期 + 刷新机制 |
| 拉黑阈值设定依据 | `BlacklistServiceImpl` | 5 条/30%/80% 为经验值；≥5 条门槛防小样本误伤，订单数=0 条件区分真实买家与职业差评 |
| 路径穿越防护 | `FileServerController` | `canonicalPath` 前缀校验，拒绝跳出上传目录的访问 |
| 统一返回与全局异常 | `Result` / `GlobalExceptionHandler` / `BusinessException` | 前后端契约一致，Controller 无 try-catch 噪音 |
| 用户身份透传 | `JwtInterceptor` → `UserContext` | 拦截器注入请求属性，Service 层静态取用，避免层层传参 |
| 商品多图存储 | `Product.images` + `JsonListTypeHandler` | TEXT 字段存 JSON 数组，TypeHandler 自动序列化/反序列化 |
| 逻辑删除与时间填充 | MyBatis-Plus 配置 + `MetaObjectHandlerConfig` | `deleted` 字段逻辑删除，create/update 时间自动填充 |
| 前端路由权限 | `router/index.js` 守卫 | guest / requiresAuth / requiresAdmin 三级 meta 控制，与后端拦截器双重保障 |
