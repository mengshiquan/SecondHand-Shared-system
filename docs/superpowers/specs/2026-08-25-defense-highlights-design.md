## 上篇 · 核心亮点提纲

### 2.1 订单状态机与超时预留回收

- 背景：C2C 场景"拍下不买"会锁死商品；并发下单可能一物多卖
- 方案：`STATUS_FLOW` 静态映射定义合法流转（PENDING→PAID→SHIPPED→COMPLETED / ↘CANCELLED），非法流转抛异常
- 实现（`OrderServiceImpl`）：
  - 下单即预留：商品转 OFF_SHELF + `expire_time` 30 分钟
  - 创建前检查是否已有他人未过期预留；同一买家旧待付订单自动取消
  - `@Scheduled(fixedRate = 5min)` 回收过期订单并恢复商品在售
  - 付款/发货/确认收货按买卖家身份分别鉴权；全程 `@Transactional`
- 答辩价值：并发、状态一致性、事务边界的思考

### 2.2 小黑屋自动风控算法

- 背景：二手交易缺信任，差评刷分、恶意用户需自动识别
- 方案：每日 3 点定时扫描（`@Scheduled(cron = "0 0 3 * * ?")`），双规则判定：
  - 卖家规则：90 天内收到 1 星 ≥5 条且占比 >30%
  - 买家规则：发出 1 星占比 >80% 且成交订单数 = 0（防职业差评）
- 实现（`BlacklistServiceImpl.autoScan`）：
  - 刑期递增：`14 天 × 2^拉黑次数`
  - 先解封到期用户再扫描，`justUnblacklisted` 集合防止解封后立即再罚
  - 受过处罚者只统计解封后的新评论，避免历史违规反复处罚
- 答辩价值：规则引擎思维 + 算法边界条件处理；文档需给足"为什么这么设计"的依据

### 2.3 投诉-申诉治理闭环

- 背景：自动规则有误伤，需人工救济通道，形成治理闭环
- 方案：
  - 投诉：PENDING→RESOLVED/DISMISSED，成立即拉黑被投诉人并通知投诉人
  - 申诉：PENDING→APPROVED/REJECTED，通过即解封并通知申诉人
- 实现：`AdminServiceImpl.handleComplaint/handleAppeal` + `t_complaint`/`t_appeal` 表 + 通知联动 + 后台待办计数（`getNotifications` 聚合 pending 数）
- 答辩价值："检测→处罚→申诉→救济"完整闭环，体现系统设计完整性

### 2.4 JWT 认证与小黑屋联动拦截

- 背景：认证和风控是横切关注点，不能散落在各 Controller
- 方案：`JwtInterceptor` 统一校验 Bearer Token → 注入 userId/role；黑名单用户仅封禁写操作（`/product/` `/order/` `/comment/` `/favorite/` 下非 GET 请求返回 403 + 解封时间），读操作放行——"可看不可动"的柔性处罚
- 实现：`JwtInterceptor` + 前端 `request.js` 401 清 token 跳登录的配合
- 答辩价值：拦截器/中间件设计、权限粒度设计

### 2.5 ECharts 后台数据可视化

- 背景：管理员需一眼掌握平台运营状况
- 方案：Dashboard 四指标卡（用户/商品/订单/今日订单）+ 分类分布玫瑰图 + 订单状态柱状图
- 实现：
  - 后端 `DashboardVO` 聚合统计（`/admin/dashboard`、`/admin/category-stats`）
  - 前端（`Admin.vue`）：玫瑰图 `roseType: 'area'` + 翠绿渐变色板；状态柱状图状态-颜色语义映射（待付款暖橙/已完成翠绿，呼应主题色体系）
  - 图表生命周期管理：`dispose` 销毁、Tab 未可见时重试渲染、窗口 `resize` 自适应、空数据兜底态
- 答辩价值：前后端数据流 + 可视化工程细节（生命周期问题常被追问）
